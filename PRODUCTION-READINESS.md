# Hivy Production-Readiness Fix List

Generated 2026-06-11 from a 12-dimension multi-agent review (streaming-correctness, sandbox-lifecycle, provisioning, security-authz, security-secrets-injection, concurrency-go, error-resilience, data-integrity, frontend-quality, rust-runtime-review, maintainability, infra-config). Findings marked **[verified]** survived adversarial verification; all others are unverified reviewer reports. Use the checkboxes as a task tracker.

## Executive summary

**Raw finding counts:** 2 critical · 43 high · 76 medium · 34 low (155 total; 55 adversarially verified). After merging cross-dimension duplicates: **34 P0 tasks, 34 P1 tasks, 52 P2 tasks**.

**The 5 scariest issues:**

1. **Cross-account session takeover** — the web proxy's process-global refresh promise hands user B user A's freshly refreshed tokens and persists them in B's cookie (`apps/web/app/api/proxy/[...path]/route.ts:94-100`).
2. **Real cards can be double-charged** — subscription renewal charges Paystack with no idempotency reference outside any transaction; any post-charge failure re-charges on the next sweep (`internal/billing/subscription/renew.go:128-142`).
3. **Every long agent turn breaks for users** — the SSE proxy is hard-killed at 2 minutes (`internal/employeeruntime/client.go:24,96`), the Rust broker's history buffer evicts the *newest* events (`sandboxes/runtime/crates/api/src/http_gateway.rs:132-133`), and the web client never retries or refetches (`apps/web/app/w/sessions/page.tsx:475-477`).
4. **The sandbox runtime tunnel is an unauthenticated open proxy** to every localhost port ≥1024 inside every sandbox, and the LLM proxy has a DNS-rebinding SSRF to internal/cloud-metadata IPs (`sandboxes/runtime/crates/api/src/tunnel.rs:171-173`, `internal/proxy/validate.go:104-114`).
5. **Paid Railway services leak forever on at least five paths** — failed warm slots, failed provisioning, duplicate employee sandboxes, and every specialist task launch leave live billing services with no reaper (`internal/sandbox/warm_pool.go:100-107`, `internal/specialisttasks/service.go:278-296`, `internal/handler/employees_sync_runner.go:19-47`).

## P0 — Must fix before launch

All critical + verified-high findings, ordered by blast radius. `[merged: ...]` notes findings reported independently by multiple dimensions.

### Security

- [x] **P0-1. Web proxy refresh single-flight leaks one user's session to another (cross-account takeover)** **[verified, critical]** `[merged: security-authz + frontend-quality]` — `apps/web/app/api/proxy/[...path]/route.ts:31, 94-100, 229-235, 295-299`. `safeRefresh()` dedupes refreshes with a single module-level `refreshPromise` shared by every user in the Node process and ignores the `refreshToken` argument when a refresh is in flight. Under ordinary concurrent load, user B awaits user A's refresh, retries their request with A's bearer, and gets A's `SessionData` encrypted into B's `__session` cookie — silent full account takeover. **Fix:** key in-flight refreshes by token hash (`Map<sha256(refreshToken), Promise<SessionData|null>>`, deleted in `finally`); never return a promise started for a different token.

- [x] **P0-2. Triage fixes-todo.txt: known P0s (API-key privilege escalation) are still unfixed** **[verified]** — `/Users/bahdcoder/code/usehivy.com/fixes-todo.txt:1-60`. The committed security TODO register lists 5 P0s; at least two are verifiably still present: P0 #1 "Narrow API keys can escalate to all" (`cmd/server/serve_routes_v1.go:93` mounts `POST /api-keys` without `RequireOrgAdmin` or a scope ceiling, so a narrow key can mint an `all`-scope key) and P0 #3 is the refresh swap above. **Fix:** gate `/v1/api-keys` behind `RequireOrgAdmin` and/or forbid keys minting scopes broader than their own; triage every remaining P0/P1 in the file and move the register to the issue tracker.

- [x] **P0-3. SSRF in LLM proxy: DNS-rebinding TOCTOU and ignored resolution errors in ValidateBaseURL** **[verified]** — `internal/proxy/validate.go:104-114`. Customer-controlled credential `base_url` is validated by resolving the host once (`LookupIP` errors silently allowed through) while the actual dial re-resolves independently — a short-TTL attacker domain passes validation pointing at a public IP, then resolves to `169.254.169.254`/`10.x`/`127.0.0.1` at dial time. **Fix:** fail on `LookupIP` error; resolve once, validate every address, and pin the dial to the validated IP (custom `DialContext` that re-checks `isDisallowedIP` on the actual remote address).

- [x] **P0-4. Client-spoofable IPs: chi RealIP trusts True-Client-IP/X-Forwarded-For unconditionally** **[verified]** — `cmd/server/serve.go:236` (also `serve_mcp.go:33`); nginx never strips `True-Client-IP` (`proxy.nginx.conf:96`). Any client can set `True-Client-IP` to bypass per-IP auth brute-force rate limiting (`auth_ratelimit.go:51`) and poison audit-log IPs. chi v5.3 deprecates RealIP as IP-spoofing-vulnerable. **Fix:** strip/override `True-Client-IP`/`X-Real-IP` at nginx, use `ngx_http_realip_module` with trusted CDN ranges, and replace `chimw.RealIP` with a trusted-proxy-aware extractor.

- [x] **P0-5. Specialist warm-claim pushes the full EMPLOYEE config (employee-mode token, prompt, all cron schedules) into specialist sandboxes** **[verified]** — `internal/employeeruntime/config_push.go:10-58` (via `internal/sandbox/orchestrator_warm_claim.go:60`, env mode at `runtime_env.go:90`). The orchestrator's single config-push callback is mode-unaware: every specialist launch on the Railway warm-pool path first configures the specialist sandbox as the employee — employee-mode proxy token, employee system prompt/MCP tools, and the employee's schedules (which `BuildRuntimeSchedules` also repoints, see P0-16). **Fix:** make the pusher mode-aware (detect specialist sandboxes via snapshot/labels): skip the push (Launch pushes the real config) or compile the specialist definition; never call `BuildRuntimeSchedules` for non-main sandboxes.

### Billing & money

- [x] **P0-6. Subscription renewal can double-charge the customer's card** **[verified]** `[merged: error-resilience + data-integrity]` — `internal/billing/subscription/renew.go:128-142, 176-228`. `ChargeAuthorization` is called with no `Reference` (the Paystack struct supports one, `internal/billing/paystack/charge.go:17`) and outside any transaction; if `applySuccessfulRenewal`'s DB tx fails or the worker dies post-charge, the hourly sweep re-enqueues and charges again. **Fix:** pass a deterministic reference (`renew-<subID>-<periodEndUnix>`) so Paystack dedupes, and/or persist a charge-in-flight marker before charging so retries verify instead of re-charging.

- [x] **P0-7. Credit-ledger idempotency tuple has no unique index; GrantWithTx is unlocked check-then-insert (double credits)** **[verified]** `[merged: error-resilience + data-integrity]` — `internal/billing/credits.go:84-101`; `internal/migrations/sql/000003_billing_usage.sql:133-137` has only plain indexes. The code's comments and `isUniqueViolation` branches rely on a unique index on `(org_id, reason, ref_type, ref_id)` that doesn't exist; concurrent grants with the same reference (e.g. double-submitted `POST /v1/billing/verify`, `internal/handler/billing_verify.go:187`) both insert — free credits. **Fix:** add `CREATE UNIQUE INDEX CONCURRENTLY ... ON credit_ledger_entries (org_id, reason, ref_type, ref_id) WHERE ref_id <> ''` and treat 23505 as already-recorded (the existing handling then becomes live).

- [x] **P0-8. Usage marked insufficient_credits is permanently written off — never billed after top-up** **[verified]** `[merged: error-resilience + data-integrity]` — `internal/tasks/billing_batch_debits.go:49-51, 125-132`; `billing_batch_process.go:92-106` stamps `billed_at` unconditionally. When balance < delta the whole batch exits the unbilled queue with `credits_debited=0`, and `successfulBilledCost` excludes the rows forever — routine for any org whose balance approaches zero mid-flight. **Fix:** leave `billed_at` NULL for insufficient rows (track attempts separately), or add a sweep that re-opens `billing_error='insufficient_credits'` rows once balance is positive.

- [x] **P0-9. GenerationWriter silently drops billable usage rows on flush error, full buffer, or shutdown timeout** **[verified]** `[merged: error-resilience + data-integrity]` — `internal/middleware/generation.go:68-76, 105-111, 113-128`. The flush clears the batch even on insert failure (up to 50 rows per DB blip), `Write` drops entries when the 10k channel is full, and shutdown abandons the queue at deadline — all directly unbilled LLM spend. **Fix:** retry failed batches with backoff or spill them to the existing asynq `generation:write` task (MaxRetry 3); treat buffer-full as backpressure for billing-bearing entries; alert on drops.

- [x] **P0-10. Runtime model-usage webhook acks 200 even when the generation insert fails** **[verified]** — `internal/handler/employee_outbound_webhooks.go:169-173` (ack at `:105`). `agent.run.model.usage` is the sole billing record for runtime LLM usage; on token/credential lookup or DB error the failure goes to Sentry only and the runtime gets 200, so the revenue-bearing row is gone forever. **Fix:** return 5xx for usage-event persistence failures so the runtime outbox retries, and derive the generation ID deterministically from `(sandbox_id, session_id, sequence)` so retries are idempotent.

### Task queue & message delivery

- [x] **P0-11. enqueue.Client silently drops task-baked asynq options (Queue/MaxRetry/Timeout) whenever Sentry trace wrapping rewrites the payload** **[verified]** `[merged: data-integrity + error-resilience]` — `internal/enqueue/client.go:43-53`. With Sentry enabled, every task enqueued from a traced context is rebuilt via `asynq.NewTask(type, payloadWithTrace)` without its options: critical-queue tasks (webhook forward `payloads.go:29-35`, trigger dispatch) land on the default queue with default retry/timeout. **Fix:** stop baking options into constructors — return `(task, []asynq.Option)` like the newer payload files and pass options at enqueue time, or wrap the trace into the payload before `NewTask`.

- [x] **P0-12. Inbound gateway messages permanently lost on transient runtime failure (dedupe tombstone + 200 to provider)** **[verified]** — `internal/gateway/service_connection.go:80-86, 120-139`; `internal/handler/nango_webhooks.go:149-154` returns 200 on error; `store.go:50-59` treats any prior row (including `failed`) as duplicate. A sandbox waking, a runtime restart, or the 2-minute post timeout silently drops the user's Slack/HTTP message with no retry anywhere. **Fix:** treat `status=failed` (or stale `received`) dedupe rows as retryable and re-run Send, or move delivery into an asynq task keyed by event ID.

- [x] **P0-13. Outbound agent replies permanently lost: failed delivery row occupies the dedupe key and is returned as success** **[verified]** — `internal/gateway/service.go:256-268`. `HandleRuntimeFinal` inserts a `"failed"` delivery row under the dedupe key after a send error; every later attempt finds it and returns it as delivered — one transient Slack API error permanently drops the reply (caller `employee_outbound_webhooks.go:239-252` also acks 200). **Fix:** retry-and-update when the existing delivery has `status="failed"`, or insert the dedupe row only after a successful send (with an in-flight marker for concurrency).

- [x] **P0-14. EmployeeTriggerDispatch is non-idempotent under retry: agents re-receive already-delivered trigger messages** **[verified]** — `internal/tasks/employee_trigger_dispatch.go:83-118`. The handler loops over triggers calling `deliver()` (irreversible `PostHTTPMessage` at `:207`) and returns the error on any failure, so asynq retries the whole batch and re-delivers triggers 1..N-1 — agents act twice (PRs, messages). **Fix:** insert a `(delivery_id, trigger_id)` row with a unique index *before* posting (insert-or-skip), or fan out one task per (delivery, trigger) with TaskID dedupe. (Pair with the missing unique index, P2.)

- [x] **P0-15. EmployeeEventWriter loses session events: acks webhooks before durable write, drops batches on DB error, and the shutdown flush runs on the cancelled root ctx** **[verified]** `[merged: streaming-correctness + concurrency-go]` — `internal/handler/employee_event_writer.go:86-92, 120-148` (ack-before-write via `employee_outbound_webhooks.go:105`) and `:70, 27-40, 150-167` (drain captures the `signal.NotifyContext` root ctx, wired in `cmd/server/serve.go:141,278-293`). A transient Postgres error permanently loses up to 100 events including `agent.message.sent` (the only durable record of replies); every graceful shutdown discards the entire 20k buffer because the flush ctx is already cancelled. **Fix:** retry failed batches with backoff or return non-2xx until durable so the runtime outbox redelivers; flush on `context.WithoutCancel(ctx)`.

### Sandbox provisioning & lifecycle

- [x] **P0-16. Sandbox rollback hard-deletes cascade-wipe all employee cron schedules (data loss)** **[verified]** — `internal/employeeruntime/runtime_schedules.go:31-35`. `BuildRuntimeSchedules` (a read path) repoints every schedule's `sandbox_id` to whatever sandbox the config is compiled for; `fk_employee_schedules_sandbox` is `ON DELETE CASCADE` (migration 000011:74) and sandbox rows are hard-deleted on several rollback paths — one failed upgrade/rollback deletes the org's schedules. **Fix:** stop mutating schedules inside compile (repoint explicitly only after a successful main-runtime push, never for specialists); change the FK to `ON DELETE SET NULL`/`RESTRICT`; stop hard-deleting sandbox rows in rollbacks.

- [x] **P0-17. ensureEmployeeSandbox is check-then-create with no lock and treats any non-'running' sandbox as absent — duplicate billing sandboxes + abandoned existing ones** **[verified]** `[merged: sandbox-lifecycle + provisioning]` — `internal/handler/employees_sync_runner.go:19-47`; selector filters `status='running'` (`internal/employeesandbox/selector.go:64-65`); no unique constraint on `sandboxes(employee_id, status)`. Concurrent syncs (org PATCH, env-var writes, Nango webhooks, model changes — which arrive together during onboarding) each provision a sandbox; losers run and bill forever; 'creating'/'stopped' sandboxes are invisible so new ones are minted alongside. **Fix:** per-employee Postgres advisory lock (or partial unique index on `sandboxes(employee_id) WHERE status IN ('creating','running')`); have the selector return creating/starting/stopped rows and route them through `EnsureSandboxActive`.

- [x] **P0-18. Failed provisioning never rolls back the provider resource — error sandboxes leak live compute with valid credentials baked in** **[verified]** `[merged: provisioning + sandbox-lifecycle]` — `internal/sandbox/orchestrator_create_employee.go:98-146` (also `:110-118` orphan when the post-create DB update fails, leaving a row with empty `external_id`; same patterns at `:246-254` and `orchestrator_create_specialist.go:105-113`). Every failure after provider-create/warm-claim (endpoint, health, config push, clone) only writes `status='error'`; the resource keeps running with the runtime secret and a 24h proxy token, invisible to the selector and never reaped. **Fix:** on any post-create failure call `provider.DeleteSandbox(context.WithoutCancel(ctx), externalID)` and revoke the minted token; add a reaper for sandboxes stuck in `creating`/`error` beyond a TTL.

- [x] **P0-19. Warm slots in 'error' or stranded in 'claiming' never get their Railway services deleted — unbounded paid-resource leak** **[verified]** `[merged: sandbox-lifecycle + error-resilience]` — `internal/sandbox/warm_pool.go:81-85, 100-107`; failure paths in `orchestrator_warm_claim.go:32-62` and `internal/tasks/sandbox_warm_pool.go:175-177`. `MarkError` only flips the DB row; nothing in the repo ever processes `error`/`claiming` slots, so every decrypt/health/config/readiness failure leaves a live billing service, and Reconcile provisions replacements on top. **Fix:** have `MarkError` (or a periodic reaper) call `provider.DeleteSandbox` on the slot's ExternalID; sweep slots stuck in `claiming` older than ~10 min.

- [x] **P0-20. Specialist sandboxes leak on every path: deletion only happens if the LLM voluntarily calls terminate, and launch failures retry into more sandboxes** **[verified]** `[merged: sandbox-lifecycle + provisioning]` — `internal/specialisttasks/service.go:164-234, 278-296`. The only provider deletion is the `specialist_task_terminate` MCP tool (`:291-294`); normal completion just marks the task `idle` (`employee_outbound_webhooks` → `markSpecialistTaskIdle`), the lifecycle sweep excludes these sandboxes, and all eight post-create failure returns in `Launch` (incl. the task-insert failure at `:219-221`, which makes the sandbox unaddressable) keep it running while telling the LLM to retry — minting another. **Fix:** deferred cleanup in `Launch` calling `DeleteSandboxResource` on any error after creation; create the task row before/atomically with the sandbox; add a TTL reaper for idle/terminated specialist tasks.

- [x] **P0-21. Health sweep blindly persists transient provider status; 'error' is terminal with no recovery and GetStatus failures are silently swallowed** **[verified]** — `internal/sandbox/orchestrator_health.go:23-39` (terminal at `orchestrator_active.go:38-39`; Railway maps any unknown deployment state to error, `railway/driver.go:157-158`). One transient CRASHED observation permanently bricks the sandbox row even though Railway auto-recovers — and P0-17 then provisions a duplicate; provider errors return silently so deleted resources stay 'running' forever. **Fix:** require N consecutive bad observations before persisting `error`; log/capture GetStatus failures; add an error→running re-probe path (or include `error` rows in the sweep).

### Rust runtime (agent availability)

- [x] **P0-22. Stale recurring cron jobs are skipped forever — fast_forward_if_stale never advances next_run_at** **[verified]** — `sandboxes/runtime/crates/runtime/src/scheduler.rs:64-84`. Recurring jobs whose lag exceeds 2× the stale threshold (any sandbox pause longer than ~max(interval, 240s)) log "fast-forwarding" and return `None` without writing a new `next_run_at`, so they are re-fetched and re-skipped every 5s poll forever — all schedules silently die after a pause. **Fix:** in the stale branch compute the next future occurrence and call `repo.update_next_run` before returning `None`.

- [x] **P0-23. Agent loop retries forever with no failure cap on request/cut-off/thinking-only/empty paths, permanently locking the session** **[verified]** — `sandboxes/runtime/crates/agent/src/runner.rs:245-299, 469-570`. Only the in-stream error path caps at 3 (`:398`); the request-failure, `model_cut_off`, `model_thinking_only`, and `model_empty_response` branches `continue` without incrementing `effective_turn` or any cap — a persistently failing model endpoint spins the turn forever and all session messages queue behind it. **Fix:** apply the same `>= N` abort (yield `AgentEvent::Error`, return) to all four branches and/or count them against `effective_turn`.

- [x] **P0-24. Model HTTP client has no timeout: a stalled provider connection hangs the turn forever** **[verified]** — `sandboxes/runtime/crates/agent/src/model_client.rs:31, 59, 316-388`. `reqwest::Client::new()` with no connect/overall timeout, and the SSE consumer has no idle deadline — half-open connections (routine during provider incidents) block `send().await` or `bytes.next().await` indefinitely; nothing upstream bounds the turn, locking the session until process restart. **Fix:** set `.connect_timeout(...)`, wrap the header phase in `tokio::time::timeout`, and wrap each `bytes.next()` in a 60-120s idle timeout surfaced as a retryable transport failure.

- [x] **P0-25. Compaction orphans tool-result messages from their assistant tool_calls message, producing API-invalid history (session bricked)** **[verified]** — `sandboxes/runtime/crates/agent/src/compaction.rs:112-132`. `find_eviction_range` sets `adjusted = tool_start + 1`, evicting the assistant message that carries `tool_calls` while retaining its tool results; providers reject the history with 400 (`InvalidRequest`, non-retryable) on every subsequent turn. **Fix:** return `Some(start..tool_start)` so assistant+tool results stay together (or extend forward past the whole tool run).

- [x] **P0-26. Byte-offset string slicing in compaction panics on multi-byte UTF-8, killing the turn task and permanently locking the session** **[verified]** — `sandboxes/runtime/crates/agent/src/compaction.rs:182, 255, 318, 326, 345`. Five truncations slice at fixed byte offsets (200/300); any emoji/CJK/accented content at the boundary panics, the spawned task dies before `finish_turn`, and the session's coordinator entry queues every future message forever. **Fix:** truncate on char boundaries (`floor_char_boundary`/`is_char_boundary` helper); also add a panic guard around the spawned handler that removes the coordinator entry.

- [x] **P0-27. Delegate completion ignores submit_or_queue's result: parent session permanently locked and the delegate result silently dropped** **[verified]** — `sandboxes/runtime/crates/runtime/src/handler.rs:820` (insert semantics at `session_coordinator.rs:29`). If the parent's coordinator entry is gone, the discarded `RunNow` result means a fresh entry was inserted that no task will ever run or remove: the sub-agent's result is never delivered and every future inbound for the parent queues forever. **Fix:** match on the result — on `RunNow`, remove the reservation or re-dispatch the notification through `inbound_sink` so a real handler runs it and calls `finish_turn`.

### Streaming pipeline (protocol → client)

- [x] **P0-28. Rust broker history keeps the FIRST 512 events: late/reconnecting subscribers replay stale history, miss the tail, and hang forever** **[verified]** `[merged: streaming-correctness + rust-runtime-review]` — `sandboxes/runtime/crates/api/src/http_gateway.rs:132-133`. `history.push(); history.truncate(512)` evicts every newly published event once a stream hits 512 (token-heavy turns exceed this easily), so reconnects/late subscribers (Slack asynq tasks, Go proxy retries) miss `final`/`done` and block on `receiver.recv()` forever. **Fix:** ring buffer (`VecDeque::pop_front` when full) so the newest events, including terminal ones, are always replayable. Do this before any client-side reconnect work (P0-30) — resume depends on it.

- [x] **P0-29. Web session SSE proxy is hard-killed after 2 minutes by http.Client{Timeout: 2m}** **[verified]** `[merged: streaming-correctness + concurrency-go]` — `internal/employeeruntime/client.go:24, 89-96`, consumed via `internal/sandbox/orchestrator.go:92` → `internal/handler/employees_session_messages.go:188-202`. Go's `Client.Timeout` covers the entire body read, so every agent turn longer than ~2 minutes has its live stream cut mid-answer with a clean-looking close (the Slack path already uses a 610s subscriber, showing the team knew). **Fix:** dedicated streaming `http.Client` with `Timeout: 0` (dial/TLS/response-header timeouts on the Transport) and explicit context/idle-read bounds.

- [x] **P0-30. Web SSE client never retries or resumes: onerror rethrows and clean server close is treated as completion** **[verified]** — `apps/web/app/w/sessions/page.tsx:475-477, 498-513`. `onerror(error) { throw error }` disables fetch-event-source's retry, so any blip — including the P0-29 kill — permanently ends the live stream with no path to the rest of the answer short of a reload, despite the broker supporting replay and the stream token being valid 1h. **Fix:** return a backoff from `onerror` while the turn is plausibly running, reconnect to the same signed stream URL (dedupe via accumulated buffer length), stop only on `done`/`final`. Depends on P0-28.

- [x] **P0-31. Sending a follow-up message wipes the previous turn's answer from the UI; persisted events are never refetched** **[verified]** `[merged: streaming-correctness + frontend-quality]` — `apps/web/app/w/sessions/page.tsx:330-336, 230-251` (no `invalidateQueries` for `employee-session-events` anywhere; staleTime 60s, no focus refetch). `startSessionStream` resets the session's stream state to `{ text: "", events: [], isStreaming: true }`, erasing the only copy of turn 1's response — every normal two-message chat visibly loses the previous answer. **Fix:** invalidate/refetch `employee-session-events` (and sessions) on stream completion; only clear the previous live state once the persisted events containing it are loaded.

### Auth availability & web app

- [x] **P0-32. Single-use refresh-token rotation races across the stream-token route, the proxy, and multiple instances — users force-logged-out** **[verified]** — `apps/web/app/api/auth/stream-token/route.ts:82-93` (also proxy `route.ts:227-245, 324-326`; backend revoke at `internal/handler/auth_refresh.go:53`). The stream-token route refreshes independently of the proxy's single-flight with a different TTL threshold (5 min vs 60s), and the per-process promise gives no cross-pod protection — concurrent refreshes use the single-use token twice and the loser clears the session cookie. **Fix:** backend grace window for refresh reuse (return the same rotated pair for ~30s) or Redis-locked refresh keyed by token hash; at minimum route the stream-token refresh through the same single-flight, align thresholds, and don't clear the cookie on 'revoked'.

- [x] **P0-33. Onboarding page enters an infinite passive-effect update loop while Slack channels load ('Maximum update depth exceeded')** **[verified]** — `apps/web/app/onboarding/use-onboarding.ts:94-116`. `channels = channelsQuery.data?.channels ?? []` makes a fresh array identity each render; the dependent memo + effect commit a new `Set([])` every cycle until React throws — onboarding crashes while the channels query is in flight. **Fix:** hoist a stable `EMPTY_CHANNELS` constant (or memoize on `channelsQuery.data`) and guard the effect with `if (selectableChannels.length === 0) return`.

### Deployment

- [x] **P0-34. Self-host production compose runs no worker and no migrations — billing, emails, and gateway deliveries never process** **[verified]** — `hosting/docker-compose.production.yml:84-118`. No service runs `/hivy work` (api image CMD is `nginx && exec /hivy serve`, `Dockerfile:40`; `cmd/server/main.go:106-110` never starts the worker in serve mode) and nothing runs `/hivy migrate up` — every asynq task piles up in Redis forever and the schema is never created. **Fix:** add a one-shot `migrate` service (`/hivy migrate up`, `depends_on: service_completed_successfully`) and a `worker` service (`/hivy work`), or run the api with `/hivy both`.

### Security & authz

- [x] **P1-1. Sandbox runtime tunnel is an unauthenticated open proxy to all internal ports ≥1024** **[verified]** `[merged: rust-runtime-review + security-secrets-injection]` — `sandboxes/runtime/crates/api/src/tunnel.rs:143-185, 171-173` (`auth.rs:16` exempts `/tunnel/`; `HIVY_TUNNEL_PASSWORD` is read in `main.rs:82-85` but never set by the control plane). `authenticate()` returns `Ok(())` when no password is configured, so any internet client can proxy HTTP/WS to any sandbox localhost port (MCP servers, dev servers, admin UIs). **Fix:** fail closed — require a control-plane-minted signed token/cookie when no password is set; always provision a tunnel secret.

- [x] **P1-2. Fail-open HMAC verification on employee outbound webhooks when the encryption key is absent** — `internal/handler/employee_outbound_webhooks.go:127-130`. `verifySignature` returns true when `h.encKey == nil` and the routes are mounted unconditionally — anonymous callers can forge session events/usage for any sandboxID in such deploys. **Fix:** return false (or don't register the routes) when `encKey` is nil.

- [x] **P1-3. ## Suggested fix order (P0 sequencing)

1. **Security first (independent, small diffs):** P0-1 (refresh keying), P0-2 (API-key escalation + fixes-todo triage), P0-3 (SSRF pinning), P0-4 (RealIP). These don't touch shared subsystems and remove the takeover/SSRF class outright. Fold in P1-1 (tunnel fail-closed) here — same severity class.
2. **Streaming protocol bottom-up:** fix the Rust broker first — P0-28 (history ring buffer), then P1-30 (queued-message `done` semantics) since the client contract depends on both; then P0-29 (Go proxy streaming client); only then the web client P0-30 (retry/resume) and P0-31 (refetch on completion) — client reconnect/dedupe logic is only correct once replay and queued semantics are fixed. P0-32 (refresh rotation race) and P0-33 (onboarding loop) are independent and can land any time; P0-32 pairs with P1-9 (atomic backend rotation) — design the grace window once.
3. **Task-queue substrate before delivery semantics:** P0-11 (enqueue options) first — every retry/queue fix below assumes options actually apply. Then P0-12/P0-13 (inbound/outbound gateway loss), P0-14 (trigger idempotency, with the P2-45 unique index in the same migration), P0-15 (event writer durability).
4. **Billing, schema first:** P0-7's unique index migration before anything that relies on 23505 handling; then P0-6 (charge reference), P0-8 (insufficient-credits requeue), P0-9 (generation writer retry), P0-10 (webhook 5xx + deterministic IDs). P0-8/9/10 change what reaches the batch debiter, so land them together and re-run billing reconciliation after.
5. **Sandbox lifecycle as one workstream:** P0-16 (schedule FK + repoint removal) FIRST — it makes the rollback deletions in P0-18/19/20 safe to add. Then build one shared "delete provider resource on failure + reaper" mechanism and apply it across P0-18 (provisioning rollback), P0-19 (warm slots), P0-20 (specialists); P0-17 (advisory lock/unique index) next; P0-21 (health-sweep debounce/recovery) last since its semantics depend on which states the reaper now owns. P0-5 (mode-aware config push) early in this stream — it also blocks correct specialist behavior.
6. **Rust runtime turn loop:** P0-26 (UTF-8 panic) and P0-25 (compaction boundary) first — they brick sessions outright; then P0-23 (retry caps) and P0-24 (model client timeouts) which define turn-failure semantics; then P0-27 (delegate coordinator) and P0-22 (cron fast-forward). Ship as one runtime image bump.
7. **Deployment:** P0-34 (compose worker + migrations) — independent, do immediately; it gates anyone self-hosting and is required to even observe the billing fixes working.
